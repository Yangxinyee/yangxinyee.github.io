Context Engineering for AI Agents: Nine Components Across Three Layers

Xinye Yang · November 24, 2026 · 4 min read

TL;DR. Context engineering is not about fitting as much information as possible into a context window. It is about delivering the right information, at the right time, with the right level of detail, while balancing intelligence, latency, cost, and reliability. I break an agent's context management system into nine components across three layers: the foundations that make an agent functional, context budget management that prevents overflow, and advanced context and persistent memory management.

Having spent considerable time both building and using AI agents, including developing Context Compaction and Memory features at a scale of millions of users, I've come to appreciate how critical a well-designed context management system is to the success of an agent product.

Context Engineering is deceptively simple in principle, yet full of subtle engineering challenges in practice.

Why it is hard: three competing constraints

  • Context windows have finite capacity.
  • Context must be processed again with each model request, making longer contexts more expensive.
  • Adding more information can actually degrade model performance.

Layer 1: The foundations, making an agent functional

1. Context assembly

Maintain a deterministic ordering: stable content first, dynamic content last.

This is essential for prefix caching. Even a small change early in the context can invalidate the subsequent cached prefix.

Codex has documented several pitfalls, including adding or removing tools mid-session, switching models, changing working directories, and inconsistent tool ordering.

One mitigation is to preserve existing messages and append updates instead of retroactively modifying them, wherever the API architecture permits.

2. Static context

System prompts, tool definitions, and project instructions.

These are included in every request, so keeping them compact is essential. With a large tool ecosystem, tool definitions alone can consume a significant portion of the context window.

Claude Code addresses this through progressive disclosure: exposing lightweight tool information upfront and loading full definitions only when needed. Skills follow a similar design philosophy.

3. Conversation history

An append-only record of interactions.

History cannot be arbitrarily truncated. Structural integrity must be preserved, particularly the pairing between tool calls and their corresponding results.

Layer 2: Context budget management, preventing context overflow

4. Tool output management

One of the largest sources of context consumption, particularly when managing a diverse ecosystem of MCP servers.

This is also one of the most failure-prone areas in production. I once dealt with a Sev2 incident related to this, which made the lesson particularly memorable.

File reads and command outputs can quickly exhaust the context window. Each tool therefore needs an appropriate output budget.

A common approach is to offload oversized results to disk, retaining only a preview and a reference to the complete output in context.

5. Token accounting and budgeting

Accurately measure token consumption before each model request and surface meaningful usage information to users.

Conceptually straightforward, but inaccurate accounting can lead to surprisingly complex production failures.

6. Context compaction

The central questions are when to trigger compaction, what information to preserve, and how to evaluate its quality.

Compaction is inherently lossy. Earlier instructions may disappear, and omissions in generated summaries are often difficult to detect.

Certain critical information, such as project instructions, should therefore be explicitly preserved or reinjected after compaction.

Compaction also typically rewrites the context prefix, requiring the prompt cache to be rebuilt.

Layer 3: Advanced context and persistent memory management

7. On-demand context loading

Retrieve information when it becomes relevant rather than injecting everything upfront.

8. Context isolation

Delegate specialized tasks to subagents with isolated context windows, preventing intermediate reasoning and tool outputs from polluting the primary agent's context.

9. Persistent memory

Automatically extract, consolidate, and refine useful knowledge across sessions, while periodically pruning or decaying outdated and low-value memories.

Closing

Ultimately, Context Engineering is not about fitting as much information as possible into a context window.

It is about delivering the right information, at the right time, with the right level of detail, while balancing intelligence, latency, cost, and reliability.

A larger context window is not a substitute for a well-engineered context management system.
